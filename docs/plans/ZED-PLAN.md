## Zed Extension Testing — Investigation (2026-03-20)

### Findings

**Zed has NO extension testing framework.** Unlike VS Code (which has `@vscode/test-electron`), Zed provides no way to run automated tests against extensions.

| Capability | Available? |
|---|---|
| Extension testing framework | **No** |
| Test API / mock host | **No** |
| Headless mode for extension testing | **No** (exists for remote dev/AI agents, not extension testing) |
| CI build validation (compile + lint) | **Yes** (compile to WASM, validate tree-sitter queries) |
| Manual dev testing via "Install Dev Extension" | **Yes** |
| Unit testing pure logic (non-API code) | **Yes** (standard Rust testing on native target) |
| WASM-based functional testing | **No viable path** (no mock Wasmtime host for Zed's WIT interface) |

### Why It Doesn't Exist

- `zed_extension_api` targets `wasm32-wasip2` using WIT bindings generated by `wit_bindgen`
- The generated code requires Zed's Wasmtime host to provide host functions
- No mock host implementation exists for testing outside of Zed
- The official `zed-industries/extensions` repo has zero tests — only compilation checks
- There are no open issues or PRs requesting extension testing infrastructure

### Our Testing Strategy

1. **Pure logic unit tests** — Extract all testable logic into `logic.rs` (no `zed_extension_api` imports). Test slash command dispatch, DAP config building, request kind detection, default config, env var lookup, binary path construction on native target
2. **LSP E2E tests** (existing) — `zed_extension_e2e_tests.rs` and `zed_extension_e2e_advanced.rs` test the LSP protocol layer that the Zed extension connects to, covering all 21 LSP features
3. **WASM compilation in CI** — ensures the extension compiles to `wasm32-wasip2` (catches type mismatches, missing imports)
4. **Clippy + fmt** — enforces code quality on the extension source
5. **Tree-sitter query validation** — should add `ts_query_ls` or similar linting for `.scm` files
6. **Manual smoke testing** — "Install Dev Extension" + `zed --foreground` for debugging

### Gap Analysis vs VS Code

| Testing Layer | VS Code | Zed |
|---|---|---|
| Extension activation | Automated (Mocha + test electron) | Manual only |
| LSP feature verification | Automated E2E | **Automated** (shared LSP E2E tests) |
| DAP feature verification | Automated integration | Manual only |
| Slash command verification | N/A | **Automated** (pure logic tests) |
| Binary resolution | Covered by E2E | **Automated** (pure logic tests) |
| DAP config building | N/A | **Automated** (pure logic tests) |
| Tree-sitter queries | N/A | Manual + lint |
| WASM compilation | N/A | **Automated** (CI) |

### Recommendation

The existing LSP E2E test suite provides strong coverage of the intelligence layer. The WASM build in CI catches compilation issues. Pure logic tests in `logic.rs` cover slash commands, DAP config, and binary resolution. The main gaps are:

- **DAP integration testing** — must be manual until Zed adds testing infrastructure
- **Extension lifecycle testing** — no automated path exists

Watch Zed's extension API evolution. The headless platform work (for AI agents) could eventually enable automated extension testing.
